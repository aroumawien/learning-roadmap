Hostinger hosting learning roadmap

Your learning plan

  1. Complete six flexible sessions: hosting concepts; local-file upload; domain and HTTPS; WordPress setup; migration; testing and maintenance.
  2. Start with your existing HTML/CSS/JavaScript roadmap. Use a separate test domain, subdomain or folder for WordPress and migration practice.
  3. Finish when you can publish your files, create a WordPress practice site and explain backup, verification and rollback.

Session 1: Hosting, domains and choosing a route

  1. A domain is the address; hosting stores and serves the website. DNS connects the domain to services. HTTPS encrypts browser-to-website traffic.
  2. For your existing code, choose a hosting setup that supports PHP/HTML websites and File Manager access. Hostinger Website Builder is a separate workflow.
  3. Compare initial and renewal costs, storage, databases, backups, email, supported runtimes and access methods. Features depend on the plan.
  4. Add a domain or use a temporary preview address if offered. Menu labels may change, so compare tutorials with current official instructions.
  5. Checkpoint: explain why your static roadmap does not need a database.

Session 2: Upload a website from your computer

  1. Test your project through a local server. Check every page, relative path, image, menu and browser-console error.
  2. Keep index.html, other HTML pages, CSS, JavaScript, images and subfolders together. Remove secrets, private files and database dumps from the upload.
  3. Compress the website contents into a ZIP. Know whether it includes an enclosing folder such as fullstack-roadmap.
  4. Create a PHP/HTML website in Hostinger. Open its dashboard, then Files → File Manager. Open that website’s public_html directory.
  5. Back up any existing website before replacing files. Do not overwrite a working WordPress installation with your static project.
  6. Upload the ZIP and extract it. For your roadmap, the intended entry should be public_html/index.html, not public_html/fullstack-roadmap/index.html. Move the extracted contents if needed.
  7. Check exact filename case and paths: hero1.png must match the uploaded filename. Preserve existing subfolders.
  8. Open the preview or live address and test inner pages. Remove the uploaded archive after verifying extraction; retain an off-site backup.
  9. Static HTML/CSS/JavaScript needs no MySQL database. A PHP/MySQL application also requires database import and configuration. A framework source folder is not necessarily its production build.
  10. Checkpoint: publish the roadmap homepage and successfully open two inner pages.

Session 3: Domain, DNS and HTTPS

  1. Record the current DNS settings, especially email and verification records, before changing anything.
  2. Use the nameservers or DNS values supplied for your specific hosting setup. If changing nameservers, preserve needed records at the new DNS provider.
  3. Website migration does not automatically move email. Domain registration can stay with the current registrar while its DNS points to Hostinger.
  4. Allow for DNS propagation. Verify the root domain and www. Confirm the SSL certificate, HTTPS and HTTP-to-HTTPS redirect; check for insecure asset URLs.
  5. Checkpoint: the chosen address works over HTTPS and existing email still works.

Session 4: Create a WordPress website

  1. Use a separate practice domain, subdomain or installation path; do not install over the roadmap.
  2. Use the WordPress setup flow or Website → Auto Installer → WordPress, depending on the dashboard. Confirm the installation domain and folder.
  3. Set the title, administrator email and unique administrator credentials. Install a current supported WordPress version.
  4. Open WordPress administration, choose a maintained theme and create Home, About and Contact pages. Set navigation, homepage and permalinks.
  5. Install only essential plugins. Configure a contact form and test email delivery. Update WordPress, themes and plugins, then back up the site.
  6. Uploading HTML files does not automatically create an editable WordPress theme. A conversion or rebuild is a separate task.
  7. Checkpoint: publish a three-page demo and successfully receive a test contact message.

Session 5: Migrate a website

  1. Route A — assisted migration: check eligibility, back up files and databases, then submit the migration/import request through Hostinger’s secure dashboard using source details or a backup.
  2. Keep the original site online. Preview and verify the migrated copy before changing live DNS.
  3. Route B — manual migration: copy website files, export the database if used, upload files, create the destination database/user and import the database.
  4. Update application database settings. WordPress normally stores these in wp-config.php. Use the actual destination host, name, username and password.
  5. When changing a WordPress domain, use a migration-aware URL replacement process; blind replacement can damage serialized data.
  6. Test media, logins, forms, redirects and permalinks. Check cron jobs, email and other integrations separately.
  7. A local WordPress move requires files and database. A WordPress content export alone is not a full-site backup. WordPress.com and proprietary Website Builder migrations may follow different rules.
  8. Checkpoint: migrate a test site and document how to restore or keep using the original.

Session 6: Verification, updates and recovery

  1. Test pages, navigation, images, downloads, forms, authentication and any database operations.
  2. Check phone portrait/landscape and desktop layouts, HTTPS, broken links and console errors.
  3. If the wrong homepage appears, check document root, index file, DNS and cache. For missing images, check paths, case, HTTPS and upload completion.
  4. For database failures, verify configuration and permissions. For failed migration, retain or restore the original while investigating the copy.
  5. Create an off-site backup and learn restoration. Keep a change log and upload only intended changes.
  6. Final project: deploy your roadmap, create a separate WordPress demo, and produce a tested backup/recovery checklist.
